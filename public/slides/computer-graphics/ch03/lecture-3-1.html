#sec-2-3

动画的关键：不是所有数据都要变

方案A：CPU重算顶点

  • 每一帧重新计算4个顶点
  • 每一帧重新上传Buffer
  • 对象复杂时，CPU→GPU传输会变重

方案B：更新一个参数

  • 顶点数据保持不变
  • 每一帧只更新 uTheta
  • 旋转计算交给Vertex Shader

随堂测验 1：动画中每帧最适合改变什么？

单选60 s

已有一个复杂模型的顶点数据保存在 GPU Buffer 中，现在只希望它持续绕原点旋转。更合理的做法是：

A每一帧重新生成全部顶点并重新上传 Buffer
B每一帧更新旋转角度的 uniform，然后重新绘制
C每一帧重新创建 Canvas 和 WebGL Context

#sec-4-1

为什么不能直接递归调用 render？

错误模型

function render() {
    update();
    draw();
    render();
}

同步递归：当前函数尚未返回，就继续调用自身。

调用栈会不断增长

render↓render↓render↓...

这不是动画循环，而是失控的函数调用。

动画循环的关键：让本次绘制结束，再把下一次绘制交还给浏览器调度。
#sec-4-2

requestAnimationFrame：把下一帧交给浏览器

它不是立即再次执行 render()，而是请求浏览器在下一次适合重绘时回调。 

function render(time) {
    gl.clear(gl.COLOR_BUFFER_BIT);
    theta += 0.03;
    gl.uniform1f(thetaLoc, theta);
    gl.drawArrays(gl.TRIANGLE_STRIP, 0, 4);

    requestAnimationFrame(render);
}
requestAnimationFrame(render);
Callback→Update→Draw→Return→Next frame

随堂测验 2：requestAnimationFrame 到底做了什么？

单选60 s

在动画程序中，requestAnimationFrame(render) 的作用最接近下面哪一项？

A立即同步调用 render()，形成普通递归
B创建一个新的线程，并保证每秒固定执行 60 次
C请求浏览器在下一次适合重绘时回调 render
D直接交换前后缓存，不需要再执行绘制代码
参考答案：C。它不是立即递归调用，也不保证固定帧率；它把下一帧绘制交回浏览器调度，从而形成更合适的动画循环。
#sec-4-5

双缓存：为什么要等“一整帧”准备好？

绘制和显示是解耦的。浏览器显示当前完整图像，图形系统在后台绘制下一帧。

Display

Front Buffer（前台缓存）

屏幕读取并显示的完整画面，防止未画完直接暴露导致撕裂。

Screen Display 🖥️
Drawing

Back Buffer（后台缓存）

GPU 进行光栅化的私有绘制区域，完成后触发 Swap 交换。

GPU Render Loop ⚙️

从动画到交互：用户改变的是状态

正方形已经会转。现在用户点击按钮，希望它反向旋转。这个操作不是直接“改变画面”，而是改变程序状态。

Click→Event→Callback→direction→Next Render 
let direction = true;

document.getElementById("DirectionButton")
  .addEventListener("click", function () {
      direction = !direction;
  });

function render() {
    theta += direction ? 0.03 : -0.03;
    gl.uniform1f(thetaLoc, theta);
    gl.drawArrays(gl.TRIANGLE_STRIP, 0, 4);
    requestAnimationFrame(render);
}

AI协作：核验一个关于 rAF 的解释

AI回答：
“requestAnimationFrame 会创建一个新的线程，并保证程序每秒运行60次，所以它比 setInterval 更快。”

找可能正确的部分
